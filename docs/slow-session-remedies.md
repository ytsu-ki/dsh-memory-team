# 0.3.0：按慢会话原因调整执行方式

依据用户提供的《近期会话响应变慢原因记录》设计。本仓库未包含原始会话、统计脚本或个人报告；文中样本数据尚未在这里独立重算，因此不将其视为模型性能基准。

| 观察到的原因 | 插件措施 | 实际边界 |
| --- | --- | --- |
| 长公式、长代码和重复解释扩大输出量 | 提示复用验证过的模板或脚本，输出文件后简述证据；长输出后提醒检查重复内容 | 不截断用户要求的内容，不设生成时限；减少量取决于模型执行 |
| 多轮探索、反复读取或失败后重复同一命令 | 项目记忆复用已验证经验；相同参数和结果累计 3 次后提醒；每 20 个工作步骤复核验收条件 | 相同结果不能证明环境未变；只提醒，不拦截操作 |
| 独立调查串行执行、子任务重复创建 | 最多两个原生子 agent，各有范围和验收标准；稳定任务标识避免重复派发 | 并行可能增加总 token 和服务端负载；依赖任务仍串行 |
| 简单子任务使用过高思考档位 | 支持显式子任务 `reasoning_effort`，省略继承；只走已开启的原生模型选择 | 不改变主模型设置，不自动开启子模型选择 |
| 工具、安装、测试、后台任务耗时 | 引导一次启动、保留任务 ID、等待原生完成通知；支持安全的独立读取批量执行 | 不会使外部程序本身变快，不会杀进程来缩短数字 |
| 审批与用户回答等待 | 区分审批和提问时间，提示合并必要问题、标明等待对象 | 保留原有权限流程，不设置自动允许规则 |
| TRANSPORT 重试 | 统计传输重试，成功进入下一模型步骤时提示检查连接边界，避免无证据扩大并发 | 不修复代理或供应商故障；请求仍失败时提醒无法被模型执行 |
| QQ 守候 | 单独统计主动等待，排除其重复检测及纯等待步骤的检查点计数 | 不改监听时间或唤醒条件 |
| 历史上下文庞大 | 按项目检索有界记忆，子 agent 使用原生默认的独立上下文 | 不强制清空、压缩历史；高缓存命中时不能假定缩短上下文必然显著提速 |

## 统计口径

- 记录中的 320 步是 7 轮合计，短版写成“单轮最多 320 步”不准确。不能据此推定单轮行为。
- 工具时间已包含工具内部的审批、问答或等待；并行任务还存在交叠。不同类别不能直接相加为总时间。
- `workflow_status` 用事件时间对每类活动区间取并集，只报告当前或最近一轮；不会从聊天文本猜测进度。`work_steps` 排除只调用等待或状态工具的步骤，与全部 `steps` 区分。
- `modelPhaseMs` 从步骤开始到模型消息或步骤结束，可能包含重试、准备和首字等待；它不是净生成时长。输出量以提交消息的可用 usage 为准，不覆盖未报告的失败输出。
- 提醒及摘要基于工具结果指纹，投影不复制参数或输出正文；原生 Harness 日志仍按原有机制保存。

## 验证效果

使用任务相同、验收条件相同的前后对照，分别比较完成质量、工作步骤、成功输出 token、重复调用、各类等待与传输重试。需要完整交付且检查通过，才能视为改进；不要把取消、少做工作或审批无人回应算作模型提速。

本地自动化测试验证机制和真实 Harness 组件集成，模型响应使用模拟数据。它们不能证明线上提速比例。建议从有明确验收的公式批量修改、已知问题修复、两个独立调查任务各取一个样本；机器人持续守候单独观察。
